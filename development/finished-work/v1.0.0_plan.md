## Release tasks covered (from RELEASE_PLAN_v1.md)

The master-plan items below keep `RELEASE_PLAN_v1.md`'s original numbering;
this plan's tasks are numbered in **execution order**, so the mapping is
noted per item.

1. Announce the stable plugin/telemetry contracts and publish the final compatibility statement across README, CHANGELOG, and docs hub. → plan Task 3
2. Promote packaging metadata from `Development Status :: 4 - Beta` to `Development Status :: 5 - Production/Stable`, only after all v1.0.0 release gates are closed and release-blocking defects are zero. → plan Task 5
3. Confirm that staging validation signed off at v1.0.0-rc remains valid, and confirm zero active deprecations. → plan Task 1

6. Tag the v1.0.0 release and circulate the upgrade checklist to partners with caching and parallelisation guidance (folded into Task 6, Release preparation, since tagging is release.md steps 11–13). → plan Task 6

## Global rules

- **Tasks are numbered in execution order.** Execute Task 1 → Task 6 in sequence: the confirmation tasks (1–2) fail fast on evidence the announcement (Task 3) cites as still valid; the docs verification (Task 4) validates all content edits; the classifier promotion (Task 5) is gated on Tasks 1–4; Release preparation (Task 6) is always last.
- **No planned implementation.** Same discipline as the RC: every task below is confirmation, announcement, or the mechanical GA cutover. A release-blocking defect is an emergency patch (separate change, full gate re-run), not a scope addition to this plan.
- **RC evidence carries forward.** Caching/parallel staging validation, the deprecation-closure gate, docstring coverage, and the schema freeze statement were all verified at RC (`development/finished-work/v1.0.0-rc_plan.md` Section 9). GA does not re-run staging validation unless a post-RC release-blocking defect was patched (per the RC→GA release gate in `RELEASE_PLAN_v1.md`).
- **Classifier promotion is GA-gated.** `Development Status :: 5 - Production/Stable` must not be set until every other task in this plan except Release preparation (i.e., Tasks 1–4) is closed.

## Task verification mappings (machine-readable)

This block is the **source of truth** for `make local-checks-task TASK=<n>`.
`scripts/local_checks.py` is a generic engine: it parses the fenced
`toml ce-task-verification` block below from the active release plan
(discovered from the project version lineage — this plan declares
`**Release version:** 1.0.0` / development version `1.0.0-dev` in its header,
matching the `1.0.0` lineage — overridable with `--plan`) and builds each
task's focused steps and lint targets from it. Without this block,
`make local-checks-task` cannot resolve any task for the active `1.0.0`
lineage, since `_resolved_plan_path` selects this file as the sole
`development/current-work/v*_plan.md` match. Task ids map to this plan's GA
tasks 1–6 (in this plan's execution-order numbering); every step is a
validation/confirmation step, consistent with the GA posture (no planned
implementation).

Step kinds: `pytest = [paths...]` (runner adds `-q`, `-o addopts=`, and
`--no-cov` when available; optional `pytest_args = [...]` are inserted after
the paths) and `command = "..."` (shell-split; a leading `python` resolves to
the active interpreter). `lint_targets` scopes the quick-profile Ruff
check/format steps; if omitted or empty, changed-file detection is used.
The engine fails fast with the supported id set when a task id has no mapping
here, so a `local-checks-task` verification line without a matching mapping
cannot pass.

command = "python scripts/local_checks.py --deprecation-closure"

[[task.1.steps]]

pytest = [
  "tests/unit/cache",

]

[[task.1.steps]]
