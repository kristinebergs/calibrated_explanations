## Release tasks covered (from RELEASE_PLAN_v1.md)

1. Announce the stable plugin/telemetry contracts and publish the final compatibility statement across README, CHANGELOG, and docs hub.
2. Promote packaging metadata from `Development Status :: 4 - Beta` to `Development Status :: 5 - Production/Stable`, only after all v1.0.0 release gates are closed and release-blocking defects are zero.
3. Confirm that staging validation signed off at v1.0.0-rc remains valid, and confirm zero active deprecations.
4. Confirm Standard-001/Standard-002 guardrails remain enforced post-tag, monitor caching/parallel telemetry dashboards, and schedule maintenance cadences for the first patch release.
5. Verify documentation hubs are current, navigable, and reflect v1.0.0 API state.
6. Tag the v1.0.0 release and circulate the upgrade checklist to partners with caching and parallelisation guidance (folded into Task 6, Release preparation, since tagging is release.md steps 11–13).

## Global rules

- **No planned implementation.** Same discipline as the RC: every task below is confirmation, announcement, or the mechanical GA cutover. A release-blocking defect is an emergency patch (separate change, full gate re-run), not a scope addition to this plan.
- **RC evidence carries forward.** Caching/parallel staging validation, the deprecation-closure gate, docstring coverage, and the schema freeze statement were all verified at RC (`development/finished-work/v1.0.0-rc_plan.md` Section 9). GA does not re-run staging validation unless a post-RC release-blocking defect was patched (per the RC→GA release gate in `RELEASE_PLAN_v1.md`).
- **Classifier promotion is GA-gated.** `Development Status :: 5 - Production/Stable` must not be set until every task in this plan (other than Release preparation) is closed.

## Minimal new tests required

No new application tests are expected for this milestone (stability
declaration only — no runtime behavior changes). If a release-blocking
defect is found and patched:

- Add the minimum focused test that reproduces the defect and passes after the fix.
- Re-run the affected task gate and Task 6 release-preparation gates.
- Record the defect and its test in the `1.0.0` release notes.

If Task 6 step 6 (`make release-postcommit`) needs `NEXT_VERSION=` exercised
